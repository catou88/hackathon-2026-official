# 硬超时修复与验证

本轮修复针对已观察到的缺陷：SDK 设置 35 秒请求超时、55 秒案例预算，真实在线案例仍耗时 75–83 秒。仅在调用前检查剩余时间，或仅给线程/Future 设置 timeout，都不能停止正在执行的请求。

## 执行机制

1. `transport.py` 在独立进程执行一次模型请求。父进程依据绝对 monotonic 截止等待，到期终止并回收请求进程。截止取请求开始后 35 秒与剩余案例时间中的更早值，并为回收、审计留余量。迟到响应不被采用。
2. 公共入口 `run.py` 默认启用 `supervision.py`。长期存活的案例 worker 保留 DuckDB 缓存，父进程监督初始化、数据查询、控制器和案例结果；第一例及重启后的第一例计入进程启动时间。内部模型截止早于外层截止，通常可先正常回退，外层负责永久卡死等异常。
3. Windows 使用 Job Object。worker 先以挂起状态创建，加入 Job 后再恢复执行，避免子孙进程在接管前逃逸。到期终止整棵进程树，确认成员进程退出后才重启。Linux 使用独立进程组，终止后检查非 zombie 成员是否已退出。未确认清理成功时停止运行，不假装已经安全恢复。
4. 每个工具完成后，保存按运行代次、row_id 隔离的原子证据快照。父进程是预测、证据、轨迹及 usage 的唯一最终写入者；确认落盘后通知 worker 继续。超时使用最近完整快照形成低置信回退。没有任何可靠组件时明确失败，不编造答案。
5. 费用以持久化模型尝试为准。没有确认 usage 的中断请求保留预留费用；resume 同时恢复整轮和未完成案例的费用上限。终止本地进程不证明服务端停止生成或计费。

外部中断后恢复不会重新授予已开始案例的时长。原截止前的同代完整答案可以恢复，否则用原证据快照结案；预测已写但证据/trace/usage 不完整时补齐产物。恢复耗时估计和停机间隔分开记录，不混称为实测案例时延。

## 已通过的本地验证

- 80 项程序回归测试，其中包含实际子进程、HTTP 等待和进程树测试；另有 5 项评测工具合成测试。
- 模拟永久卡死工具：4 秒案例配置下约 3.44 秒截停，孙进程已退出，$0.031 的合成未知费用预留仍在，随后下一例正常完成。
- 整轮配置 3 秒、案例配置 8 秒时，整轮约 2.72–2.75 秒结束。
- 前一代 worker 的快照不会被当前案例采用；快速返回、最终退出卡死、截止前后响应和中断后费用均有覆盖。
- Windows 轮询读取与原子替换竞争曾造成 PermissionError，现对替换作最多 150 毫秒的短重试。

这些进程验证在本机 Windows 上完成。Linux 路径已实现，但 Docker 内资源与截止行为仍需实测。操作系统调度和最终文件写入存在小量开销，监督器预留了清理时间；不能把配置值表述为任何系统故障下的数学实时保证。

## 范围与评测

整例监督由公共 CLI 提供。直接在已有进程调用 `adapter.solve` 的集成方仍须提供外层案例监督；其模型请求已使用独立进程截止，数据查询仍有 DuckDB interrupt。强制重启会丢弃内存查询缓存和服务熔断状态，费用不会重置。

全开发集使用固定源码和配置，先离线后 routed，各跑 70 例，按 20/20/20/10 分批。每例 55 秒、每批 1200 秒；四个在线批次共享费用预算。预算不足时继续生成回退预测，并将“是否尝试模型”和“是否采用模型”分开报告。标签只传给离线评分器。

这是一轮开发集对照，不是隐藏测试、留出集或 single/routed 重复实验。完整结果见 `out/full70-hard-timeout-20260917/REPORT.md`，其机器可读结果和源码哈希分别为 `results.json`、`manifest.json`。
